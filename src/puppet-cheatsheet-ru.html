Шпаргалка по Puppet

Ресурсы и манифесты, классы и модули, переменные и факты, зависимости и уведомления, шаблоны и данные Hiera, команды агента и сервера, проверка и отладка.

Как это работает

  • Манифест (.pp) описывает желаемое состояние системы, а не шаги по его достижению.
  • Ресурс — единица описания: пакет, файл, служба, пользователь.
  • Каталог — собранный для конкретного узла набор ресурсов; агент приводит систему к нему.
  • Факты — сведения об узле, собранные Facter: система, адреса, память.
  • Идемпотентность: повторный запуск ничего не меняет, если состояние уже верное.

Ресурс

package { 'nginx':
  ensure => installed,
}

file { '/etc/nginx/conf.d/site.conf':
  ensure  => file,
  owner   => 'root',
  group   => 'root',
  mode    => '0644',
  content => template('web/site.conf.erb'),
  require => Package['nginx'],
  notify  => Service['nginx'],
}

service { 'nginx':
  ensure => running,
  enable => true,
}

Тип ресурса пишется строчными буквами (package), ссылка на него — с заглавной (Package['nginx']).

Частые типы ресурсов

package
ensure: installed, latest, absent или конкретная версия
file
ensure: file, directory, link, absent; content, source, mode, owner
service
ensure: running или stopped; enable — автозапуск
user / group
Учётные записи: uid, groups, shell, home
exec
Команда; обязательно ограничьте unless, onlyif или creates
cron
Задание по расписанию: command, hour, minute
host / mount
Записи в /etc/hosts; точки монтирования

Порядок и уведомления

require => Package['nginx']
Выполнить после указанного ресурса
before => Service['nginx']
Выполнить до указанного
notify => Service['nginx']
При изменении уведомить ресурс — служба перезапустится
subscribe => File['/etc/app.conf']
Обратная сторона notify: следить за чужими изменениями
Package['nginx'] -> File['/etc/site.conf'] ~> Service['nginx']
Цепочка стрелками: порядок и уведомление

Классы и модули

class webserver (
  Integer $port = 80,
  String  $doc_root = '/var/www',
) {
  package { 'nginx': ensure => installed }

  file { '/etc/nginx/conf.d/app.conf':
    content => epp('webserver/app.conf.epp', {
      'port' => $port,
    }),
    notify  => Service['nginx'],
  }

  service { 'nginx':
    ensure => running,
    enable => true,
  }
}

include webserver

class { 'webserver':
  port => 8080,
}

Раскладка модуля: manifests/, templates/, files/, data/, spec/. Имя файла соответствует имени класса: webserver::ssl живёт в manifests/ssl.pp.

Переменные, факты, условия

$packages = ['curl', 'htop']
Массив; хеш — { 'ключ' => 'значение' }
$facts['os']['family']
Факты узла: семейство системы, версия, адреса
if $facts['os']['family'] == 'Debian' { ... }
Условие
case $facts['os']['name'] { 'Ubuntu': {...} default: {...} }
Ветвление по значению
$pkg = $facts['os']['family'] ? { 'Debian' => 'apache2', default => 'httpd' }
Выбор значения по условию
package { $packages: ensure => installed }
Один ресурс для каждого элемента массива

Переменные в Puppet неизменяемы: присвоить значение второй раз в той же области нельзя.

Шаблоны

epp('модуль/файл.epp', { 'port' => $port })
Шаблон на языке Puppet с явными параметрами — предпочтительный вариант
template('модуль/файл.erb')
Шаблон ERB: переменные доступны как <%= @port %>
file { ...: source => 'puppet:///modules/web/app.conf' }
Готовый файл из каталога files/ модуля

Разделяйте код и данные: логика — в модулях, значения для сред и узлов — в Hiera.

Отладка и осторожность

  • Начинайте с --noop: видно намерения без изменений на узле.
  • notice() и --debug помогают понять, какие значения подставились.
  • Дублирование ресурса — частая ошибка: один файл не может описываться дважды; выносите его в класс.
  • exec без ограничивающего условия выполняется каждый раз и ломает идемпотентность.
  • Тесты модулей — rspec-puppet, проверка на реальной системе — Litmus или запуск в контейнере.
