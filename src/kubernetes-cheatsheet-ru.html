Шпаргалка по Kubernetes

Объекты кластера, повседневные команды kubectl, манифесты Deployment и Service, настройки и секреты, обновления и откаты, диагностика неполадок.

Основные объекты

  • Pod — минимальная единица запуска: один или несколько контейнеров с общей сетью и томами.
  • Deployment — поддерживает нужное число подов и управляет обновлением без простоя.
  • StatefulSet — для приложений с состоянием: устойчивые имена и тома.
  • DaemonSet — по одному поду на каждый узел (агенты, сбор журналов).
  • Service — постоянный адрес и балансировка между подами.
  • Ingress — маршрутизация внешнего HTTP-трафика по именам и путям.
  • ConfigMap и Secret — настройки и чувствительные данные отдельно от образа.
  • Namespace — логическое разделение кластера на области.

Какие типы объектов поддерживает кластер и их сокращения

Осторожно: перед изменениями проверяйте текущий контекст — команда, отправленная не в тот кластер, самая частая причина аварий.

Deployment

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3
  selector:
    matchLabels: { app: api }
  template:
    metadata:
      labels: { app: api }
    spec:
      containers:
        - name: api
          image: registry.example.com/api:1.4.2
          ports: [{ containerPort: 8080 }]
          env:
            - name: LOG_LEVEL
              value: info
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits:   { cpu: 500m, memory: 512Mi }
          readinessProbe:
            httpGet: { path: /health, port: 8080 }
            initialDelaySeconds: 5

requests — сколько гарантированно выделяется и по чему планировщик выбирает узел; limits — верхняя граница. Превышение памяти приводит к принудительному перезапуску контейнера.

Service и Ingress

apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  selector: { app: api }
  ports:
    - port: 80
      targetPort: 8080
ClusterIP
Тип по умолчанию: адрес доступен только внутри кластера
NodePort
Порт на каждом узле — обычно для тестов
LoadBalancer
Внешний балансировщик у облачного провайдера
api.prod.svc.cluster.local
Внутреннее DNS-имя; внутри пространства имён достаточно api
Ingress
HTTP-маршруты и TLS; требует установленного контроллера

Настройки и секреты

kubectl create configmap app-config --from-file=app.conf
Настройки из файла
kubectl create secret generic db --from-literal=password=...
Секрет из значения
envFrom: [{ configMapRef: { name: app-config } }]
Подключить все ключи как переменные окружения
volumeMounts + volumes
Подключить как файлы в контейнере

Важно: данные Secret хранятся в кодировке base64, а не в зашифрованном виде. Шифрование на стороне кластера или внешнее хранилище настраивают отдельно.

Обновления и откат

kubectl set image deploy/api api=api:1.4.3
Обновить образ и запустить поочерёдную замену подов
kubectl rollout status deploy/api
Следить за ходом обновления
kubectl rollout history deploy/api
История версий
kubectl rollout undo deploy/api
Вернуться к предыдущей версии (--to-revision=N — к конкретной)
kubectl rollout pause / resume
Приостановить и продолжить обновление

Состояния подов

  • Pending — нет подходящего узла: не хватает ресурсов или не выполняются ограничения размещения.
  • ImagePullBackOff — образ не скачивается: опечатка в имени, нет тега или доступа к реестру.
  • CrashLoopBackOff — контейнер падает и перезапускается: смотрите logs -p.
  • OOMKilled — превышен лимит памяти; поднимайте limits или ищите утечку.
  • Evicted — узел вытеснил под из-за нехватки ресурсов или места на диске.
  • Terminating надолго — под держит завершение: проверьте preStop и грациозное отключение.

Диагностика

kubectl get pod <имя> -o yaml
Полное описание с текущим состоянием
kubectl describe node <узел>
Ресурсы узла, ограничения и размещённые поды
kubectl get pods --field-selector status.phase!=Running
Только проблемные поды
kubectl auth can-i create deploy -n prod
Проверить собственные права
kubectl apply --dry-run=server -f m.yaml
Проверка манифеста без применения
kubectl diff -f m.yaml
Что именно изменится в кластере

Полезные привычки

  • Манифесты хранить в репозитории, а не менять объекты вручную командами.
  • Всегда указывать конкретный тег образа: latest делает выкладку непредсказуемой.
  • Задавать requests и limits — без них планировщик работает вслепую.
  • Добавлять readiness- и liveness-пробы: первая убирает под из балансировки, вторая перезапускает зависший.
  • Алиас alias k=kubectl и автодополнение экономят массу времени.
